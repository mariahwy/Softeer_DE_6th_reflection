## 1. Review
Spark 최적화는 어플리케이션 자체가 아니라 데이터 기반으로 개별 Job을 최적화하는 과정임을 깨달았다.
데이터 포맷은 대체적으로 컬럼 기반의 Parquet가 유리하다.
또한 Spark가 인메모리 툴이라고 면접에서도 얘기했었는데, 엄밀히 말하면 그게 아니라 LRU 캐시 기반이며, 메모리 부족 시 디스크 Spill이 일어난다.
Spark SQL을 활용하면 Catalyst Optimizer가 자동으로 최적화하지만, Partition 수·크기와 Skew 처리(Salting, Broadcasting)는 직접 실험을 통해 튜닝이 필요하다.
Spark Web UI와 History Server로 Shuffle Time·Disk/Memory Utilization을 분석하고 DAG를 개선해야 한다.
사실 5주차의 개인 미션을 하면서 Spark Web UI를 사용했었고, 특히 W5M1을 할 때(RDD) job이 10초만에 끝나면 접속이 불가한 문제가 있어서 sleep으로 10분간 기다리게 하여 캡처했었다.
또, M2에서는 잘 보였는데, M1에서는 DAG가 안 보여서 의아했었는데, DataFrame일 때만 보인다는 사실을 깨달았다. 저번 주차 미션의 의문이 모두 풀리는 기분이었다.
결국 Spark 최적화란 데이터 변화에 따라 DAG를 수정하는 지속적인 대응 작업이며, 완벽한 DAG는 없다.

팀 프로젝트를 위해서 주말을 갈아넣었지만, 우리가 만든 아이디어가 모두 kill 당했다... (최종 프로젝트 시작할 때는 멘토링까지 듣고도 아이디어를 갈아엎는 팀이 우리가 될지 몰랐다)
그래도 같이 고민하고 협력하는 과정에서 팀워크가 매우 좋아진 것 같다. 협업 과정이 재미있어서 포기하지 않고 계속 할 수 있는 것 같다! 마무리까지 최대한 열심히 해봐야겠다.

## 2. Keep (잘한 점)
iteration 돌리는 과정이 힘들어도 포기하지 않고 뭐라도 써보려고 한 점 (퀄리티는 좋지 않지만...)

## 3. Problem (문제점)
iteration 한 번이 짧지만 그래도 퀄리티가 있어야 된다고 생각하는데, 모든 아이디어가 별로였던 것 같다.

## 4. Try (구체적인 개선 방안)
iteration 한 번에 좋은 아이디어를 내려고 하지 말고, 이번에 시간이 부족해서 구체화를 덜 시킨 아이디어는 다음 iteration에 발전시켜 보거나 할 것이다.

## 1. Review
오늘은 Threads 단일 게시물 크롤링 파이프라인을 설계하고 구현했다.
Threads는 JavaScript가 매우 복잡해 기존 requests나 bs4 방식으로는 데이터 수집이 어렵다는 한계가 있었다.
이를 해결하기 위해 Playwright를 활용하여 실제 브라우저 환경을 시뮬레이션하고, 숨겨진 JSON 데이터를 추출하여 nested_lookup과 jmespath로 파싱하는 방식으로 접근했다.
최종적으로 단일 게시물의 본문, 작성자 정보, 댓글까지 구조화된 JSON 형태로 수집하는 데 성공했다.
내일은 이를 어떻게 적재할 것인지 다른 팀원들과 상의해보고, 실제 적재까지 진행할 것이다.
그리고 우리 팀의 경우 비교적 차량 관련 사고나 리콜이 빈번한 미국을 기준으로 데이터를 수집하기로 했는데, 이를 위해 IP를 미국으로 수정하고,
SNS 크롤링용으로 Cookies.json을 설정해야했다. 지금까지는 그냥 Lambda에서 실행하기 위해 S3에 Cookies.json을 저장하고 이를 일일이 함수 실행시마다
불러오는 식으로 처리했는데, 이렇게 되면 보안상의 이슈가 있다는 사실을 깨달았다. 이를 위해 S3 내부에 암호화하여 저장하거나, 아니면 아예 EC2를 크롤링할 때마다
껐다가 재부팅하는 목적의 Lambda를 작성하여 최대한 S3에 개인정보를 저장하지 않는 방식으로 수정해볼 예정이다.
또, 크롤링을 지금은 로컬에서만 해봤는데 분산환경에서도 돌려볼 생각이다.

## 2. Keep (잘한 점)
- 기술 스택 선정
단순 HTML 파싱이 아닌 Playwright를 통해 자바스크립트 렌더링 후 데이터 수집 가능성을 확보해서, 기존의 twikit api를 사용해서 크롤링하던 twitter 채널을
수집할 때도 내가 작성한 코드를 그대로 사용할 수 있을 것 같다.
JSON 파싱 과정에서 네트워크에서 graphql로 쿼리를 일일이 모니터링하면서 jmespath와 nested_lookup을 적절히 조합하여
깊게 중첩된 구조에서도 원하는 key를 추출할 수 있었다. 앞으로 이런 류의 크롤링은 문제 없을 것 같다.

- 레퍼런스 문서와 공식 라이브러리 활용
Playwright 공식 문서, scrapfly 블로그 등 레퍼런스를 참고하고 일일이 읽어보고 이해하여 로직을 구현했다.
또 이 과정을 전부 문서화해두었기에 팀원들에게 설명도 용이했다.

## 3. Problem (문제점)
팀원들과 트러블슈팅을 공유하기로 했지만, 각자 한 내용을 이해 못해서 트러블을 정리해서 올려도 집단지성으로 해결이 불가능하다.

## 4. Try (구체적인 개선 방안)
트러블슈팅시 자기가 지금까지 했던 코드등을 전부 문서화해두고, 관련 기술 스택에 대한 간단한 설명도 첨부해둔다. 혹은 관련 기술 블로그라도
첨부해두어 팀원들이 일일이 기술을 검색하지 않아도 빠르게 습득하고 문제에 대한 해결방법을 함께 논의할 수 있도록 한다.
